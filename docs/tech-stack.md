# Reso 技术栈选型

整理日期：2026-11-12。依据[项目分析会话](codex://threads/01a1d046-d5fc-7562-94e1-08389a28687c)及本项目后续 Redis、DeepSeek 模型与豆包语音讨论。本文件保留选型依据；2026-11-13 已按核心选型完成本地 MVP，实际范围见文末。产品范围与权限以 [产品需求](prd.md) 为依据。

## 选型依据与状态

用户提出先做 **React＋TypeScript 移动端 Web，后续使用 Tauri 2 发布 App**；同时明确要求：**不要考虑维护成本，优先考虑 Agent 效果。**

主对话与 Agent 模型采用用户指定的 **DeepSeek，通过 DeepSeek API 接入**；具体型号与版本在效果评测后锁定。

语音转写采用用户指定的 **火山引擎豆包语音识别大模型（ASR）**；具体识别接口与资源版本在短录音效果及延迟验证后锁定。

在这一要求之后，会话中的最新推荐调整为 **Node.js＋TypeScript＋Fastify＋LangGraph.js＋PostgreSQL**。LangGraph.js 是讨论建议，用户尚未明确批准最终框架；PRD V2.1 本身没有确定模型、Prompt、框架或独立 Agent 数量。

早期以交付成本为依据的 AI SDK `ToolLoopAgent` 推荐不再作为当前首选。Pi Core 仍是可比较方案，但不与 LangGraph 或 AI SDK 叠加两套 Agent 执行循环。没有同场景评测证据证明任一框架的对话效果更好。

## 技术栈建议

| 层次 | 会话建议 | 状态与边界 |
| --- | --- | --- |
| 前端 | React＋TypeScript，Vite 构建 | 用户提出 Web 优先路线；版本已记录于 package-lock.json |
| App | Tauri 2 | 复用前端静态资源，连接同一套 API；需早期真机验证 |
| 通用图标 | `lucide-react` | 已用于本地前端 |
| API | Node.js 受支持 LTS＋TypeScript＋Fastify | 承载认证、鉴权、校验、消息及业务接口 |
| Agent 主编排 | LangGraph.js | 最新建议，用显式状态、分支及检查点支持效果优化 |
| 数据库 | PostgreSQL | 正式业务数据、事件、授权、纠错与审计 |
| 消息分发与短期状态 | Redis，按需启用 | 多实例事件广播、共享限流、在线状态与热点缓存；正式记录仍存 PostgreSQL |
| 数据访问 | Drizzle ORM | 本地 MVP 已采用 |
| 身份认证 | Better Auth | 本地 MVP 已采用；对象与事件权限由业务层实现 |
| 后台任务 | pg-boss，API 与 Worker 分进程 | 本地 MVP 已采用，用于异步回复、重试与调度 |
| 消息传输 | HTTP POST＋SSE | 发送命令，接收消息与状态；断线按游标恢复 |
| 文件 | 对象存储 | 按权限管理图片与获准保留的语音等附件 |
| 方法检索 | 先按标签与条件查询审核方法卡 | 大量资料检索出现实际需求后再评估 pgvector |
| 主对话与 Agent 模型 | DeepSeek，DeepSeek API | 用户指定模型方向；具体型号与版本按中文对话、纠错和工具调用效果评测后锁定 |
| 语音转写 | 火山引擎豆包语音识别大模型（ASR） | 用户指定；录音转成文字，用户修改或确认后发送；具体接口、资源版本与设备兼容性待验证 |

前后端、Worker 与 PostgreSQL 已实现本地 MVP，依赖版本记录在 package-lock.json。DeepSeek 与豆包 ASR 接入代码已完成，凭据待用户配置，实际供应商调用尚未验收。

## 系统职责

```text
React 移动端 Web / Tauri App / 专业人员 Web
                       ↓
Fastify：认证、授权、消息、问卷、事件、邀请、预约
                       ↓
LangGraph.js：理解、策略决策、方法调用、回复生成与检查
                       ↓
DeepSeek 模型（DeepSeek API） / 审核方法库 / 受限业务工具

PostgreSQL 保存正式记录；Worker 处理异步任务；对象存储保存附件。
Redis 按需承担 Worker 与 API 实例之间的事件广播，以及共享限流与短期缓存。
```

后端初步按业务模块组织为单体服务：账号与授权、会话与消息、问卷与反馈、Agent、方法与练习、真人服务。模型负责理解与提议；代码负责权限、正式计分、状态变更、实际执行与输出校验。模型密钥留在服务端。

Fastify 是 Node.js 的后端接口框架，负责接收请求、校验、调用业务和返回结果；它不决定 Agent 的理解质量。

## DeepSeek 模型接入

主对话、事件理解、策略判断和回复生成使用 DeepSeek。先用同一候选主模型建立评测基线，再依据效果决定是否为不同职责配置不同型号或思考模式；不预设全部节点开启深度思考。

由服务端的 LangGraph 节点调用 DeepSeek API。DeepSeek 提供 OpenAI 兼容接口，API 地址为 `https://api.deepseek.com`；配置模型标识与 API Key，选定 TypeScript 客户端后验证实际兼容性。密钥仅保存在服务端，模型标识与 Prompt 版本随评测和运行记录保存。[官方接入说明](https://api-docs.deepseek.com/)

型号验收需覆盖中文多轮倾听、拒绝与纠错、跨轮一致性、函数调用和结构化卡片输出，同时测量回复延迟。JSON 输出按所选型号与 API 的能力配置；JSON 格式合法后，服务端仍执行字段、证据和业务校验，并处理空白响应、截断、失败与重试。[官方 JSON 输出说明](https://api-docs.deepseek.com/guides/json_mode/)

## 豆包语音转写

语音输入使用火山引擎豆包语音识别大模型（ASR）。豆包语音提供流式识别与录音文件识别，具体接口按短录音识别准确率、返回延迟、开通条件和浏览器录音格式兼容性验证后确定。[官方产品说明](https://docs.volcengine.com/docs/doubao-voice/product-overview-22?lang=zh)

首期流程为：前端录音 → 服务端调用豆包 ASR → 返回可编辑文字 → 用户修改或确认后发送 → 进入正常聊天与 Agent 流程。转写结果先作为输入草稿，未经用户发送不写成正式聊天消息。

ASR 使用豆包语音自身的接口与鉴权，服务凭据仅保存在服务端。原始录音默认仅用于转写，临时文件按转写任务清理规则处理，长期留存需另行明确授权。实现时验证录音权限、格式、转写失败与重试、取消及重复提交处理。

## Redis 的用途与启用条件

Redis 纳入可选技术栈，单实例首版无需强制部署。它主要支持消息分发与运行效率，Agent 理解与决策质量仍通过模型、上下文、方法库和评测优化。

| 场景 | 处理方式 |
| --- | --- |
| 多个 API 实例持有不同用户的 SSE 连接 | 用 Redis Pub/Sub 将 Worker 或其它 API 实例产生的事件通知广播到相关实例，再向有权接收的客户端推送 |
| 跨实例限流与在线状态 | Redis 保存共享计数与带过期时间的在线心跳；在线状态只作提示，不作为房间成员或访问权限依据 |
| 咨询师公开目录、审核方法卡等热点查询 | 在出现查询瓶颈时启用缓存，设置失效规则与版本 |
| 后台任务、重试与调度 | 继续使用基于 PostgreSQL 的 pg-boss，不因加入 Redis 再增加第二套任务队列 |

消息先写入 PostgreSQL，再发布事件通知。Redis Pub/Sub 不保存历史，订阅者断线期间的通知可能丢失，因此 SSE 重连及实例订阅恢复后按数据库游标补发，并保留定期对账机制，覆盖写库成功但通知发布失败的情况。Pub/Sub 仅承担实时通知，不作为消息唯一来源。[官方交付语义说明](https://redis.io/docs/latest/develop/pubsub/)

聊天、事件记忆、分享授权、问卷与审计的正式记录保存在 PostgreSQL。授权撤回和成员校验必须依据当前有效权限，不能只等待 Redis 缓存过期；广播通知优先只携带事件标识与版本，API 实例读取或推送内容前重新校验权限。

Redis 故障时，聊天与业务状态仍可从数据库恢复，实时推送允许延迟；跨实例限流等依赖 Redis 的功能需明确定义故障行为，不能静默绕过。房间并发控制及操作幂等仍由数据库约束和任务执行规则保证，不能仅凭短期 Redis 锁判断业务是否已经执行。

## Agent 设计

### 用户身份与内部场景

对外只有统一的 Reso 身份。PRD 保留三类内部职责，可分别组织执行流程与上下文，不据此推断必须运行三个独立模型或进程。

| 内部场景 | 读取范围 | 主要产出 |
| --- | --- | --- |
| 初步了解 | 必要账户与同意、当前问卷答案及计分 | 初始发现、经用户确认的摘要 |
| 1v1 支持 | 确认过的初始摘要、本人私聊、私人事件与练习 | 理解与回应、练习、事件记忆、分享草稿 |
| 1vN 沟通 | 当前房间成员、公开消息、有效分享快照 | 异步主持、双视角核对、共识或纪要草稿 |

1v1 角色不直接读取 SCQA 原始作答与计分；需要改变时先修改数据契约。专家只能读取相应服务授权内的资料。

### 受约束的动态决策

```text
校验消息、鉴权与持久化
          ↓
独立安全检查
          ↓
组装获准上下文 → 事件与心理线索理解 → 策略决策
                                            ├─ 继续倾听
                                            ├─ 澄清事件或解释
                                            ├─ 开展练习
                                            ├─ 提议多人沟通
                                            └─ 衔接真人支持
          ↓
生成候选回复 → 检查证据、权限与适配性 → 保存并发布
          ↓
记录用户反馈、更新理解与状态版本
```

策略可以停留、跳转和回退。会话状态 S0–S8、本轮判断 `TurnAssessment`、路由 A–H、工具与卡片是不同层次；A–H 是策略或工作节点，不是八个独立 Agent，也不是必须依次执行的八步。

本轮判断需记录意图、情绪、事件清晰度、用户意愿、候选策略、证据消息 ID 与不确定性。不能把“妈妈可能焦虑”等推测写成确认事实。用户否认后，要让后续读取的记忆、卡片与策略实际变化。

模型、理解、决策、生成与检查职责先分清，再用评测决定是否需要独立模型或额外审查 Agent；不预设某个固定调用次数能获得最佳效果。

### 正式数据与执行边界

- 分开保存来源陈述、当前理解和系统决策，记录说话人、证据、确认级别与版本。
- PostgreSQL 保存正式业务记录；框架运行上下文与检查点不能替代事件、授权和纠错记录。
- 组装上下文之前执行权限过滤，摘要与附件继承来源权限。
- Agent 提出邀请、分享或预约；用户确认后，业务接口重新鉴权并执行，使用幂等标识避免重试产生重复操作。
- 分享使用具备对象、范围与版本的快照，不随私人内容变化自动扩张。
- 前端只接收允许展示的文字、固定类型与版本的卡片、练习和业务状态；不把内部推理过程直接发送给客户端。

### 多人房间与消息发布

先保存参与者消息，再决定 Reso 是否发言，可合并短时间连续消息并允许暂不回复。同一房间需要并发控制；运行记录引用消息与授权版本，发布前重查，避免旧任务回复已经变化的情境或泄露已撤回内容。

数据库是正式记录来源，SSE 传递新消息和状态，客户端按游标补发。妈妈次日加入可以开启新一轮处理，不必让单次 Agent 任务持续挂起一天。

会话建议首版先完整生成并校验，再发布内容，SSE 可先传“已收到／处理中”等状态；这一策略增加首字等待，需要实测后决定流式输出边界。

### 方法库与效果评测

方法卡需包含适用目标、进入条件、禁忌、引导步骤、退出条件、来源及审核版本。访谈资料应先脱敏、区分原话与分析、经过专业筛选，不能默认全部作为标准话术或直接进入通用知识库。

围绕同一模型、同一资料和相同多轮案例对比编排方案，使用未参与调试的案例，由专业评审盲评：理解准确性、提问诱导性、策略适配、用户拒绝处理、纠错后变化、跨轮一致性、权限与安全边界。模型、上下文与方法库贡献应分别做对照，不能归功于框架名称。

同时验证卡片合法性、重复执行、多人并发与延迟。同一人的回访材料放在同一数据分组，防止示例与测试相互泄漏。

## Web 与 Tauri 边界

React 承载聊天、问卷、卡片、练习、事件房间与关系记录；后端承载 Agent、权限、记忆、计分和预约；Tauri 接入必要的系统分享、链接唤起、安全存储、录音和通知能力。

App 内打包前端静态资源，Web 与 App 共用源码、分别构建。家长继续通过 HTTPS 邀请链接参与；App Links 和 Universal Links 等唤起能力单独配置验证。缺少合适插件时可能需要 Kotlin／Swift，不能把 App 阶段估算为纯打包。

早期最小包重点验证：输入法与聊天滚动、录音权限、登录恢复、邀请回跳、前后台切换；通知能力单独验证。微信内登录、录音和邀请也需真机测试。

## 图标与素材

会话对 21 张 UI 的检查认为 Lucide 可覆盖大多数通用功能图标，建议 24px、1.75–2px 描边并统一使用。托手与关系导航等轮廓可能需近似图标或少量自定义 SVG。

微信品牌标志、Reso 角色与表情、人物头像、练习插画和音乐封面保留独立素材。渐变、阴影、在线点与容器用 CSS；可扫描邀请二维码按真实链接生成，不能用 `qr-code` 图标代替。正式产品无需照搬截图里的手机系统状态栏。

## 建议推进顺序

1. 先补齐本期范围、状态异常表和 Agent 验收集，明确题本、授权与安全规则。
2. 跑通 Web 登录、私聊、消息持久化、权限隔离与纠错；尽早建立固定评测集。
3. 完成问卷、小发现和一种练习，验证理解与拒绝处理。
4. 跑通事件、有限分享、另一账号受邀加入与多人沟通，形成核心闭环。
5. 尽早做最小 Tauri 真机包，继续完善真人服务、人工支持与回访。

2026-11-13 已完成移动端 UI 演示与浏览器流程检查，当前对话、问卷、分享和咨询申请均为本地演示，未接入真实服务。尚未进行 Agent 框架原型对比、服务端压测或手机真机验证。主要未决项是 DeepSeek 具体型号、Prompt、版本、部署地区、豆包 ASR 接口与资源版本、专业安全审核与运营接收流程。

## 2026-11-13 本地实现状态

已采用 React＋TypeScript＋Vite、Fastify、LangGraph.js、PostgreSQL 17、Drizzle、Better Auth 和 pg-boss。API 与 Worker 分进程，业务数据与授权落库；HTTP POST 写入，SSE 通知与定期查询对账。单实例使用 PostgreSQL LISTEN/NOTIFY，Redis 保持可选，尚未部署。

Agent 使用显式安全、理解策略、回复和校验节点。私聊使用本人当前事件、聊天、确认摘要、保存的练习与近期回访；公开房间只使用公开标题、房间历史、各自观点，以及全体当前成员均获授权的相同摘要。发布回复前检查上下文版本及权限，变更后丢弃过期结果。两种会话各自取得来源明确的理解核对记录；咨询纪要不进入任何 Agent 上下文。推测不自动执行邀请、分享或预约。

DeepSeek 模型由 `DEEPSEEK_MODEL` 配置，当前默认 `deepseek-flash` 作为待评测基线。豆包使用大模型非流式输出 WebSocket 接口 `wss://openspeech.bytedance.com/api/v3/sauc/bigmodel_nostream`，独立 API Key（或旧版 APP ID＋Access Token）和资源 ID；浏览器录音转换为 PCM，转写后确认发送，音频仅驻留内存。真实联调中 DeepSeek 已通过，豆包仍返回 401 授权匹配错误，具体见 [provider-check.md](provider-check.md)。

本版已完成 Tauri 2 Android 本机调试包及 AVD 基础验收，运行依赖本机 Web/API 和 ADB 转发，见 [Android 说明](android.md)。尚不包含生产 App 发布、附件对象存储、完整专业方法库、生产邮件验证/找回与专业危机体系。SCQA 使用项目原始校订稿的 24 题与八个独立均分，原稿保留在 [scqa-source.html](scqa-source.html)，不得宣称正式量表效度或临床效果。启动、配置和本地专业人员测试流程见 [README](../README.md)。
